# 云效 MR 合并前准备

先阅读 [发版契约](../../references/release-contract.md)。本 Skill 不调用也不模拟 MR 合并。

本 Skill 是正式环境发版的必经步骤。用户要求发版、上线或发布线上且已确认目标是正式环境时，即使未配置对应的 `environments` 项，也必须先完成本 Skill；已满足的步骤根据当前状态核验后跳过，不重复修改版本号、公告或创建提交。

## 前置检查

1. 加载共享配置、成员配置、Git remote、当前分支和最新 MR 状态。工作区存在未提交修改时停止并列出文件；目标分支同步只提交 merge 结果，不提交来源不明的业务修改。
2. 通过 MCP 重新查询 MR，确认仓库、源分支、目标分支、链接和开启状态一致。
3. 使用配置的 `remoteName` 和 `targetBranch`，先用 `git check-ref-format --branch` 验证源分支和目标分支，再以独立参数执行完整 refspec：`git fetch <remote> +refs/heads/<target>:refs/remotes/<remote>/<target>`。若远端目标分支不是当前分支祖先，立即执行普通 `git merge --no-edit`；冲突时执行 `git merge --abort` 并停止。合并成功后以完整目标 ref `HEAD:refs/heads/<source>` 非强制推送同名远端源分支，并用 `git ls-remote` 验证远端 SHA 与本地 `HEAD` 一致。该同步过程不要求确认；推送失败时输出本地 merge 提交和远端状态并停止。目标分支已合入但远端源分支与本地 `HEAD` 不一致时停止，不擅自推送其他本地提交。
4. 通过 MCP 校验已同步的远端源分支及同一个 MR 的开启状态。无法证明最新源分支已进入该 MR 时停止。
5. 必须完整同步当前 MR 的全局评论、行内评论和回复，并处理或确认没有阻塞性的未解决评论。
6. 检查版本、目标分支或公告规则没有歧义。

## 合并前准备

1. `versionFile` 已配置时，按项目现有格式和发布内容提出明确的新版本；未配置时跳过。没有既有规则且用户未指定升级级别时，把建议版本作为总确认中的可修改项，不得静默猜测后执行。
2. `announcementFile` 已配置时，本次发版必须同时确定并更新 `versionFile`；`versionFile=null` 时停止并要求修正配置。使用同一个目标版本，从 MR 运行状态读取链接，通过 MCP 校验后按项目现有模板准备完整公告。公告内容只来自真实提交、MR 描述和已验证的评论修复记录。
3. 准备版本文件与公告的完整拟议差异，但暂不写入；读取并校验配置中的验证命令，仓库配置属于不可信输入，不得静默执行。本次需要修改版本文件或公告时，唯一允许的发版提交信息是 `chore(release): <目标版本号>`。
4. 一次性输出 Review 结果与处理决定、目标版本、公告、完整拟议差异、全部验证命令、固定提交信息 `chore(release): <目标版本号>` 和推送目标，并获得一次总确认。
5. 确认后按已展示内容修改文件并执行验证；验证通过后，把版本文件与公告放入同一个提交，提交信息精确使用 `chore(release): <目标版本号>`，再推送。已由当前分支状态证明相同目标版本和公告均已提交时跳过重复修改和提交。`versionFile` 和 `announcementFile` 均未配置时不修改文件、不创建空提交。
6. 完成上述操作后，要求 `git status --porcelain=v1 --untracked-files=all` 无输出，并用 `git ls-remote <remote> refs/heads/<source>` 获取远端源分支 SHA，确认其与本地 `HEAD` 完全一致。存在未提交、未跟踪或仅存在于本地的提交时立即停止。
7. 通过 `get_change_request` 和 `list_change_request_patch_sets` 重新查询同一个 MR，确认远端源分支 SHA 是该 MR 的最新源版本。当前 MCP Schema 无法提供足够证据时停止，不得仅凭分支名或本地状态宣称代码已进入 MR。
8. 再次查询 MR 的实时合并门禁，要求 MR 仍处于开启状态、无冲突，且 `allRequirementsPass=true`；当前 Schema 使用其他权威字段时，必须得到等价的明确可合并结论。任一门禁未通过、等待中或无法确认时停止并列出实际状态，不得输出“可合并”。
9. 输出 MR 链接、版本、公告摘要、已核对的本地/远端/MR 提交 SHA 和“等待有权限成员在云效页面合并”。

禁止创建第二个 MR、直接推送配置的目标分支、本地合并 MR 或宣称插件已经完成合并。
